# xPST 1.3.0 — release-candidate notes

Status: **prepared, not published.** The version bump, the changelog entry and
these notes are the release candidate; no tag has been cut and nothing is on
PyPI yet. See [Release status](#release-status) for what is still blocking a
real release.

The canonical entry for this version is the `[1.3.0]` section of
[CHANGELOG.md](../../CHANGELOG.md); the release tooling extracts that section
into the GitHub Release notes. This document is the human-readable release
candidate: what changed in user-facing terms, the measured numbers behind it,
and what an operator needs to know before upgrading.

## Headline: the rate-limit safety program

1.3.0 is a safety release. It does not add destinations or change the posting
contract; it makes the failure path visible, bounded and testable. Every number
below was produced by the suites named next to it, on this repository's own
fake provider transports — no live post is required to reproduce any of it.

### A throttled post is now visible instead of mysterious

An active rate-limit cooldown used to exist only in a JSON file under the config
directory. Now `xpst health` and `xpst doctor` print each active cooldown with
its remaining time, strike count and the reason that was recorded, and the MCP
registry gains `xpst_rate_limit_status` (the registry is now 42 tools) for
agents that need to ask "why is nothing posting?".

All three surfaces read one module (`xpst.rate_limit_status`), so they cannot
report different answers. The read is pure local state: one file load, no
writes, no sleeps, no provider call — it is safe inside a health check, in a dry
run, and in a loop. A missing file (a fresh install) or a corrupt one reports
`idle`/`unknown` rather than raising.

The semantics every surface repeats: **a cooldown defers posts to the affected
platform; it does not fail them**, and posting resumes when the pause expires.

### One throttled Instagram post, one retry layer

On the Instagram instagrapi path (`instagram.auth_mode: session`) the uploader
retried a throttle internally *and* the service retried the whole upload, so one
throttled post cost 16 provider requests and roughly a minute and a half of
sleeping before giving up. That multiplication is what turned a single 429 into
a burst the provider could see.

The uploader now hands a throttle straight back and the service's retry layer
owns the retry. Measured in `tests/test_rate_limit_failure_injection.py` after
the fix:

| Instagram (session mode) fault shape | provider requests | sleeping |
| --- | --- | --- |
| 429, error code 4, no `Retry-After` | 4 | ≈15 s |
| 403 with a rate-limit body | 4 | ≈15 s |
| 429 with `Retry-After: 900` | 1 | no retry backoff |

The request counts are exact and asserted. The sleep column is a measurement,
not a constant: the uploader applies a randomised 1–3 s anti-ban delay before
each attempt, so one throttled post lands between roughly 14.5 s and 16.5 s
across runs, against a 19.5 s ceiling that the suite enforces.

The recorded pre-fix cost was 16 requests / ~91–98 s for the same shapes. The
budget is no longer a comment: `xpst.utils.request_budget` derives the worst
case from the live uploader and service constants, and
`tests/test_retry_economy_budget.py` fails if a nested retry layer comes back.

### Retry ownership: a terminal answer is respected

An adapter that has already given up declares the failure terminal. The retry
layer used to ignore that declaration and retry on the error text alone; it now
treats `retryable=False` as authoritative — one call, no retry, no sleeping —
while still letting the cooldown learn about the throttle and still completing
the read-back that proves an unknown outcome did or did not land. A
provider-declared `Retry-After` that outlasts the retry plan ends the retry
instead of asking a provider inside a window it just named. A hint the plan can
cover still retries, so short throttles recover in the same call.

`tests/test_retry_ownership_contract.py` pins all of it and fails if a new call
site ships retryable-looking error text next to `retryable=False`;
`scripts/audit_retryable_sites.py` prints every declaration as a table for
review.

### A failure-injection suite instead of a promise

`tests/test_rate_limit_failure_injection.py` drives scripted fake transports at
each provider SDK boundary — a mock HTTP transport for the Facebook Graph
client, a fake async client for the Instagram Graph path, a fake twikit client
for X, a fake `videos().insert()` request for YouTube — across 429,
429 + `Retry-After`, 403 with a rate-limit body, and 500 responses. No socket is
opened and no live post is possible.

It asserts, per destination and fault shape: the throttle pauses the
destination; the pause is the provider's own `Retry-After` when it sent one; one
logical post stays bounded in requests and sleeping; a rate-limited post is
never recorded as posted; the pause survives a process restart and is honoured
by the next post; one destination's cooldown never blocks another; and one
destination's cooldown never shortens a longer cooldown already running for a
sibling on the same upstream pool.

## Upgrade notes

- No configuration migration and no state migration. Existing cooldown files,
  schedules and the post ledger are read as before.
- `xpst health` and `xpst doctor` output gain a rate-limit cooldown block; JSON
  consumers gain a `rate_limit_cooldowns` key next to the existing fields.
- MCP clients that enumerate tools will see 42 tools instead of 41; the new one
  (`xpst_rate_limit_status`) is read-only and needs no mutation opt-in.
- Nothing is removed. Destinations that were disabled before this release stay
  disabled; nothing is re-enabled implicitly.

## What this release does not claim

- No destination was re-enabled and no live posting behaviour was changed by the
  version bump. Posting stayed paused through the whole safety program.
- The numbers in this document are from the test suite's fake provider
  transports, not from a live platform run. They pin the request and waiting
  economy; they are not a measurement of platform-side behaviour.

## Release status

Prepared:

- [x] `CHANGELOG.md` entry for 1.3.0
- [x] version bump across every release surface (Python package metadata, the
      runtime version, the desktop shell manifest and lock, the UI package and
      its lock, and the release-version check)
- [x] `uv.lock` regenerated for the new version; `uv lock --check` exits 0
- [x] these notes

Still blocking a real release:

- **PyPI trusted publisher is not registered for this repository**, so
  `.github/workflows/publish-pypi.yml` still fails with `invalid-publisher`.
  Registering the publisher is a one-time, human, roughly ten-minute step in the
  PyPI project settings; until it is done, the release can be built and tagged
  but not published to PyPI.
- **The tag itself is not cut here.** It is cut once the release-candidate PR is
  green and the tag lanes (Python package, desktop installers) are ready, so a
  red build never publishes a version number that cannot be reused.
- `docs/INSTALL.md` still describes v1.2.1 as the latest *published* release.
  That is correct until 1.3.0 is actually published, and it is updated as part
  of publishing, not as part of this candidate.

## Verifying this candidate

```bash
python scripts/verify_release_version.py --expected 1.3.0   # all surfaces agree
uv lock --check                                             # lockfile matches pyproject
python -m pytest tests/test_rate_limit_failure_injection.py \
                 tests/test_retry_economy_budget.py \
                 tests/test_rate_limit_visibility.py \
                 tests/test_retry_ownership_contract.py -q  # the safety program
```

Once an install of this version is running:

```bash
xpst health --json      # includes rate_limit_cooldowns
xpst doctor             # prints active cooldowns and what resumes when
```

MCP clients can call `xpst_rate_limit_status` with no arguments for the same
read-only view.
