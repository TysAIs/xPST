# xPST 1.3.0 — release candidate notes

**Status: release candidate. No tag has been cut.** This document exists so the
version bump, the changelog and the distribution work can be reviewed together
before anything is published.

`CHANGELOG.md` is the authority for what changed; this file covers what a person
installing 1.3.0 needs to know and what the release still cannot claim.

## The headline

The desktop app can update itself, honestly, on both macOS architectures.

Before this release the update channel existed but could not do its job:

- the in-app check only ran when `XPST_UPDATER_CHECK=1` was set — an E2E
  harness variable — so an installed copy was never told a newer release
  existed;
- `updates/latest.json` advertised a `darwin-x86_64` payload whose `sha512` and
  signature were the arm64 ones, so an Intel Mac downloaded a file Tauri always
  refused;
- Windows and Linux had no manifest key at all.

1.3.0 fixes all three:

- the app checks once at launch and shows a banner when a release is available;
  About → Updates has "Check for updates" and "Download and install". Installing
  is always a user action.
- the release lanes build both macOS architectures natively (arm64 on
  `macos-latest`, Intel on `macos-15-intel`) and publish each under its own
  correctly-named payload.
- Windows (`windows-x86_64`, NSIS installer) and Linux (`linux-x86_64`,
  AppImage) now carry real manifest entries.
- the manifest generator refuses the two shapes that produced the bad Intel
  entry: two platform keys describing different files with one `sha512`, and a
  bare macOS bundle name with no architecture in it.

## Upgrade notes

- **Intel macOS:** on 1.2.1 the update could not verify. The published manifest
  no longer lists `darwin-x86_64` until an Intel build exists; 1.3.0 provides
  one. Users on 1.2.1 should install 1.3.0 from the Releases page once rather
  than expecting the old update path to work.
- **Apple Silicon macOS, Windows, Linux:** the 1.2.1 → 1.3.0 update is the first
  one that can be delivered in-app. It is still subject to the signing gap
  below.

## What this release does not claim

- **Not code-signed yet.** macOS installers are ad-hoc signed and not
  notarised; Windows installers are unsigned. The repository has no Apple or
  Azure signing credential (`gh secret list` carries only the PyPI token and the
  updater keypair). The release lane now fails a `v*` tag before building rather
  than publish unsigned installers that look signed, so a real tag needs:
  - Apple Developer Program membership ($99/yr), providing
    `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`,
    `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`;
  - Azure Trusted Signing ($9.99/mo), providing `AZURE_TENANT_ID`,
    `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`,
    `AZURE_TRUSTED_SIGNING_ENDPOINT`, `AZURE_CODE_SIGNING_ACCOUNT`,
    `AZURE_CERTIFICATE_PROFILE`.
- **No install → update → boot cycle has been recorded per platform yet.** That
  evidence needs signed installers (Gatekeeper/SmartScreen intervene otherwise)
  and real machines. The credential-free half — four platform builds, four
  signed updater payloads, a four-key manifest that is re-hashed against the
  released bytes — is exercised with a `dryrun-tauri-*` tag.
- **PyPI is still unpublished.** `pypi.org/pypi/xpst/json` has no project; the
  wheel is on the GitHub release only. Whether to claim the name or retire the
  lane is an operator decision.
- **No tag was cut for 1.3.0.** This branch is a release candidate; tagging is a
  separate, explicit decision.
