# xPST 1.3.0 — release notes

**Status: release candidate. No tag has been cut.** This document ships with the
release prep so the version bump, the changelog and the distribution work can be
reviewed together before anything is published. Tagging is a separate, explicit
decision — see `docs/RELEASE.md` and `docs/RELEASE_CHECKLIST.md` for the publish
steps.

`CHANGELOG.md` is the authority for what changed, item by item. This file covers
what a person installing 1.3.0 needs to know, what changed in behaviour, and what
the release still cannot claim.

## What this release is

1.3.0 is the first release since **v1.2.1 (2026-09-25)**, and it is a large one:
the engine gained a rate-limit safety stack, a phone-first upload/confirm/publish
flow, opt-in destinations with format routing, a durable scheduling engine and a
bring-your-own-developer-app path; the desktop app now checks for updates on
launch and the release channel can describe a payload for every platform and
architecture it builds; and the surfaces that report
readiness were corrected so that a gate reading them cannot pass something the
command would refuse.

## The six defects this release is built around

These were the last blockers between "mostly works" and "will not lie to a
caller". Each is cited by pull request so it can be reviewed on its own.

- **#349 — one Meta Graph API version, pinned.** Instagram, Threads, Facebook,
  Messenger, the resumable-upload host and the OAuth consent dialog all build
  their URLs through `xpst.utils.graph_api` (`GRAPH_API_VERSION`, v26.0). Before
  this, the family was split across v19.0 (removed by Meta 2026-05-21), v20.0
  (removed 2026-09-24) and v21.0/v22.0, so parts of the Meta path were calling
  versions that no longer exist. `tests/test_graph_api_version.py` greps `src/`
  and fails on a new `graph.facebook.com/vNN` literal.
- **#351 — a dry run cannot report `"ready": true` while listing a hard
  blocker.** Readiness came from the destination plan alone, so a request the
  content contract refused (text to TikTok, which publishes video only) printed
  `ready: true` beside the blocker that refused it and then exited 1. Readiness
  now requires plan-ready **and** an empty merged blocker list **and** a posting
  destination, in the CLI, the MCP dry run and the HTTP preflight together.
- **#357 — `preflight --transform` emits the rendition plan it was asked for.**
  The service computed the per-destination `TransformPlan` and the serialiser
  dropped it, so only `verify-media --plan` ever showed the decision. Each
  destination now carries `transform` / `transforms`, and `None` means
  "not computed", never "passthrough". Advisories that were JSON-only (soft
  dimension/bitrate ceilings, faststart, non-native audio rate) now print under
  each destination and say whether the destination re-encodes or merely warns.
- **#358 — visibility is scoped, and `status` health is labelled historical.**
  Only YouTube honours an upload-time visibility; X and TikTok accept
  `visibility` on the delete path only and publish publicly. `post` now names the
  destinations that will ignore the flag instead of implying "nothing gets posted
  publicly". And `xpst status`'s `platform_health` counters, which come from local
  post outcomes, now carry `historical: true` / `source: state_history` plus a
  `platform_health_note` pointing at `xpst doctor` — TikTok could show 195
  "failures" from a retired API path while health was `all_clear`.
- **#359 — implicit queueing is refused on a paused deployment.** A manual post
  fired outside the posting window (08:00–23:00) was deferred to the schedule
  store, which *creates* `~/.xpst/schedule.json` — a schedule change nobody asked
  for. `schedule.posting_paused` (or `XPST_POSTING_PAUSED=1`) makes the deferral
  refuse instead: nothing queued, nothing uploaded, CLI exit 1 with
  `{"paused": true, …}`, MCP an error result. An explicit in-window post or
  `--now` still publishes.
- **#360 — the pause guard is asserted against the store the CLI actually
  writes.** The regression read the in-memory `config.config_dir`, which is not
  the file's directory, so "nothing was queued" was vacuously true. It now globs
  the sandbox for `schedule.json`.

## Rate limiting: what changed, and the numbers

The rate-limit stack (persistent per-platform cooldowns, one verdict per limit,
senders that refuse rather than truncate, honest readiness) is described in the
changelog. The two figures that matter for review are deterministic assertions,
not samples:

- **One throttled Instagram post on the instagrapi session path costs at most 4
  provider requests** (`MAX_ATTEMPTS_IG_SESSION = 4`, one request per service
  attempt). It used to cost 16 — the uploader retried 4× internally and the
  service retried that whole upload 4× again.
- **The wait ceiling the suite enforces is 19.5 s** for that post
  (`MAX_WAIT_IG_SESSION_S`), against roughly 96 s for the nested loop. The
  individual sleeps are jittered (`random.uniform(1.0, 3.0)` before an attempt,
  ±0.5 s on the backoff), so any single observed total varies between runs: read
  the ceiling as the enforced bound and the request count as the reproducible
  quantity.

The counted dry run (`python -m xpst.rate_limit_dry_run`) is the exit condition
for the posting pause and is reproducible on demand. Re-measured for this release
candidate:

```
scenarios: 47   platforms: facebook, instagram, tiktok, x, youtube
provider requests: 94 (publish attempts 65)
rate-limit responses: 45   cooldowns engaged: 30
posts that WOULD have gone out: 11
deferred by cooldown: 12   failed: 6   unaccounted: 0   posts lost: 0
dropped requests (never sent, by design): 30 (18 retries skipped inside a declared window)
reproducibility: runs=2 identical=True
invariant violations: 0
```

The digest of those counts is not quoted as a constant anywhere: it changes
whenever the fault matrix or a count changes, so re-run the command before citing
it.

## Behaviour changes to look for when upgrading

- **Destinations are opt-in.** `--platforms` no longer defaults to every enabled
  platform. An explicit set wins, `--all` is the explicit "every connected account
  that accepts this format", and the default is the format route ∩ connected
  accounts. A script that relied on the implicit "all" must pass `--all`.
- **Readiness and exit status.** A pre-upload content refusal exits 1; a
  per-destination blocker is reported per destination and does not abort the run.
  `ready` is false whenever there is a blocker (see #351).
- **Destination states are a closed vocabulary**, including the non-failures:
  `posted`, `skipped_unconnected`, `unsupported_format`, `refused_by_community`,
  `failed`, and `deferred` (a cooldown/anti-bot deferral, never a failure).
- **`XPST_CONFIG_DIR` owns its credential files.** Two configurations no longer
  share one credential store, and the analytics ledger resolves from the config
  directory instead of a hardcoded `~/.xpst/analytics.db`.
- **MCP accepts `mcp[cli]` up to `<3.0.0`.** The server registers against either
  SDK line and reads `isError`/`inputSchema`/`serverInfo` through accessors.
- **`schedule.posting_paused` exists.** On a paused deployment, an out-of-window
  manual post is refused rather than queued.

## Distribution and the update channel

- The updater is **on by default in the app**: it checks once per launch, shows a
  banner when a release is available, and installing is always a user action.
  `XPST_UPDATER_CHECK=0` disables the network check.
- Both macOS architectures are native release builds (arm64 on `macos-latest`,
  Intel on `macos-15-intel`), so both updater keys can carry a real payload.
- Windows (`windows-x86_64`, NSIS) and Linux (`linux-x86_64`, AppImage) now carry
  real manifest entries, with their `.exe.sig` / `.AppImage.sig` sidecars carried
  into the manifest instead of being dropped by the flatten step.
- Manifest generation refuses the shapes that produced the bad Intel entry: two
  platform keys describing different files with one `sha512`, and a macOS bundle
  with no architecture in its name.
- **A `v*` tag fails before building when the Apple or Azure signing credentials
  are absent.** `dryrun-tauri-*` tags stay open for credential-free rehearsals.

## What this release does not claim

- **Not code-signed or notarised.** macOS installers are ad-hoc signed and not
  notarised; Windows installers are unsigned. The repository holds no Apple or
  Azure signing credential. A real tag needs Apple Developer Program membership
  and Azure Trusted Signing — see `docs/tauri-updater-production.md`.
- **No install → update → boot cycle recorded per platform.** That evidence needs
  signed installers (Gatekeeper/SmartScreen intervene otherwise) and real
  machines.
- **PyPI is still unpublished.** `pypi.org/pypi/xpst/json` has no project; the
  wheel ships on the GitHub release. Claiming the name (or retiring the lane) is
  an operator decision.
- **Intel macOS ships without the lancedb-backed knowledge base.** lancedb has no
  x86_64 macOS wheel; that lane installs `[mcp,dashboard,windows]` and `xpst kb
  doctor` names the missing extra.
- **Posting stayed paused for this entire release cycle.** No live post was made
  to prove anything in this document. The engine behaviour above is proven by the
  suite and the counted dry run, both of which run with the provider wire replaced
  by scripted fakes and a socket guard; the destinations disabled in config
  (Instagram, Threads, Facebook, Messenger) are a configured Meta pause, not a
  fault.
- **No tag was cut for 1.3.0.** This branch is release prep.
