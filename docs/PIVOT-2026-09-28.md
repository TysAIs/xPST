## 1. Build vs. adopt — honest comparison

Two credible self-hostable competitors moved onto our thesis since
`docs/COMPETITIVE_EDGE.md` was written (2026-08-24). That doc's claim "no
competitor ships an MCP server" is **now stale** and we should stop repeating
it in README-adjacent copy.

### Postiz (AGPL, self-host or cloud)

- 30+ platforms, web UI, REST API, and **a first-party MCP server with ~13
  tools** (integration list, schedule/publish, posts list, AI image/video
  generation, clipping). Hosted MCP endpoint with OAuth sign-in; a skill + CLI
  for terminal agents (it explicitly lists Hermes Agent as a supported client).
- Where they win: platform breadth, team/organizations, polished calendar UI,
  AI media generation bundled in.
- Where they don't touch us: the hosted MCP surface puts your accounts and
  media through **their** servers; self-hosting means running their full
  Laravel/Postgres/queue stack. Their MCP surface is a thin scheduling facade —
  no delete-verification, no preflight, no credential health, no fail-closed
  mutation guards, no local state you can audit.

### Mixpost (self-hosted Laravel, Lite tier free)

- 11 networks, calendar, inbox, team roles, REST API, **an MCP server for
  caption-and-schedule flows**.
- Video: **remux-only by default** — full re-encode is opt-in
  (`MIXPOST_VIDEO_TRANSCODING=false` ships that way) and explicitly documented
  as "better suited to dedicated applications." There is no per-platform
  encode profile; one format goes in, roughly that format goes out.
- Lite tier gates most platforms behind paid editions; no agent-native
  mutation guards; no local encrypted credential story comparable to ours.

### What xPST actually is, differentiated

Three properties none of the field ships together, verified in this repo:

1. **Local-first.** One process (or desktop app), `~/.xpst/` is the whole
   footprint, Fernet/scrypt-encrypted credential store by default, zero
   personal data in the repo or telemetry, no server to babysit. Nothing leaves
   the machine except the platform API calls you chose to make.
2. **Agent-native surface: 40 MCP tools** (34 `xpst_*` + 2 `messenger_*` + 4
   `kb_*` — measured by `scripts/generate_counts.py` over a real stdio
   handshake, CI-enforced; the audit-era "28 tools" is the v1.0.0 count and is
   superseded). Typed errors, fail-closed mutation guards
   (`XPST_MCP_READONLY` / `XPST_MCP_REQUIRE_CONFIRM`), audit logging of every
   mutating call, dry-run everywhere, recorded-vs-live analytics labels.
   Postiz's 13 tools schedule posts; our 40 let an agent *operate* the fleet
   and be refused safely when it shouldn't.
3. **Short-form re-encode pipeline.** `encode_for_platform()` runs a real
   per-destination profile (1080×1920 portrait, CRF/GOP tuned) with
   compliance-skip fidelity invariant, caching, and partial-output cleanup —
   the video arrives cut for each platform, which neither Postiz (remux +
   passthrough) nor Mixpost (transcode opt-in, no profiles) does.

**Conclusion: build, don't adopt.** Postiz/Mixpost optimize for teams
coordinating a calendar; xPST optimizes for a person (or an agent) operating a
pipeline on their own hardware. If we adopted Postiz we would be running a
Laravel stack, routing media through someone's server, and re-implementing our
own re-encode upstream anyway. The corollary is what the rest of this memo is
about: *stop growing sideways.* Breadth (more platforms, more features) is
Postiz's game and we lose it; depth on the three properties above is ours, and
today it has exactly three unfinished edges.

## 2. The only remaining real gaps, and the work plan for each

Everything else on the capability truth table is either live-verified
(YouTube, X, Instagram), correct-by-design source-only (TikTok as source), or
honestly labelled missing (Threads/Messenger disabled). Those labels are
product truth, not bugs. The three gaps below are the ones that change what a
user can actually do.

### 2a. TikTok app audit — drafts → live Direct Post

Today: OAuth `video.upload` scope lands uploads as **inbox drafts** (PR #266);
`draft_mode: auto` tries Direct Post first and falls back on the
`unaudited_client_can_only_post_to_private_accounts` refusal. Drafts are
reported PENDING, never as published. ≤5 pending drafts per 24h. This works
and is honestly reported — but it is not publishing.

What the audit requires, step by step (TikTok developer-app review):

1. **Public website for the app** — a real URL TikTok's reviewers can visit.
   For xPST that is the GitHub Pages/README surface at
   `https://github.com/TysAIs/xPST` (or a small pages site); it must show what
   the app does and who runs it.
2. **Privacy policy URL + terms-of-service URL** — public, app-specific. These
   can be minimal, but they must exist and match the requested scopes (what we
   collect: video files, publish state; nothing else).
3. **Demo video** — a screen recording walking the reviewer through the
   integration: OAuth consent → upload → publish (or the draft flow until
   approval) → result state. The desktop-app walkthrough we already do for
   releases doubles as the source footage.
4. **Request the `video.publish` scope** on the existing app (client key
   ending …cb29fb2) — today we consent only `video.upload`. Draft-mode
   fallback code (`_unaudited_client_refused`) stays; it is correct either way.
5. **Submit for audit and wait** — TikTok's approval is discretionary, roughly
   2–8 weeks. No queue position is purchasable; nothing on our side shortens
   it except having 1–4 already true.
6. **Flip the config after approval** — `draft_mode: "never"` becomes the
   normal mode; Direct Post goes public through the container model. Then
   verify live: one real public post, `xpst analytics` reading it back through
   the already-shipped Content Posting metrics path.

Owner reality: steps 1–5 need a human with the TikTok developer account
(Alex). No code change is required for step 6 — the mode switch is config.
Expected code after audit: zero, plus a truth-table row update in the PR that
flips the default guidance.

### 2b. Threads auth

Threads is fully implemented against Meta's official Threads API
(container-publish model) but disabled/unauthenticated. What enabling it needs,
in order:

1. **Meta app + Threads API product** — add "Threads API" to a Business app at
   developers.facebook.com; add the Threads account as a tester and accept the
   invite in the Threads app. Development mode is fine for a personal account;
   no formal audit was required for the API's publish scopes at the time of
   writing (re-verify before starting).
2. **Long-lived access token + user ID** — 60-day lifetime, refreshable
   (xPST has the refresh path); configured via
   `accounts.threads.graph_access_token` and `threads_user_id` in
   `config.yaml` — deliberately not in the interactive `connect` wizard.
3. **The structural catch: no upload endpoint.** The Threads API fetches
   `video_url`/`image_url` **from a server you host**. The dashboard is
   loopback-only, so publishing local video requires a publicly reachable
   media URL — a tunnel (Cloudflare Tunnel/ngrok) or a small object-store
   hand-off. This is the only real engineering decision left: ship a
   `--serve-public-media` tunnel helper, document BYO-hosting, or mark Threads
   video as out of scope and ship text/image only. Recommendation: **text/image
   first** (no new infrastructure), video behind a documented tunnel recipe.
4. Limits to respect (already tracked): 250 posts/day, 5-min/1-GB video,
   500-char caption.

Owner: steps 1–2 are Alex (Meta account); step 3 is one acceptance-card-sized
decision + follow-through.

### 2c. Messenger auth

Messenger is the auto-reply/messaging surface (ManyChat-lite), **not a video
destination** — say so wherever it's listed. What enabling it needs:

1. **Meta Business app with the Messenger product**, a Facebook Page you
   administer, and the Page connected under Messenger → Settings.
2. **A long-lived Page Access Token** (starts `EAAG…`) + **App Secret**
   (verifies inbound webhook signatures) + a **verify token** — the config
   keys (`page_access_token`, `app_id`, `app_secret`, `verify_token`) and
   encrypted store are already in `config.py`; platform defaults to
   `enabled: false`.
3. **A publicly reachable webhook** — Meta must reach
   `/webhook/messenger` on the dashboard (default port 8080), so the same
   tunnel problem as Threads. Post-#272 the webhook registers
   fail-closed: no app secret, no subscription — good behavior, but it means
   the app secret is non-optional once enabled.
4. Page-scoped 24h messaging window governs free-form replies; reply_rules +
   auto_reply already exist.

Owner: all of it is Alex-side account work plus a tunnel; no code gates it.

### 2d. Thin analytics — the truth, and why that's the end of it

The honest picture after the D5 work (PR #212) and the metric-capability
contract (`ANALYTICS_METRIC_FAMILIES` in `analytics.py`):

- **YouTube, Instagram, X:** real metrics from official APIs. Done.
- **TikTok:** real metrics **when OAuth destination creds exist** —
  `/v2/post/publish/video/list/query/` at 6 req/min. No token → reported
  MISSING, not zero. Becomes genuinely useful the moment 2a lands.
- **Threads:** the API exposes publish/delete, **no metrics endpoint exists**.
  We return `()` and the UI renders "unavailable." There is nothing to build;
  scraping it would reinstate the fabricated-zero lie we just deleted.
- **Facebook/Messenger:** messaging surfaces; per-post engagement is out of
  the video-pipeline scope.

So "thin analytics" is not a gap we can close with effort — it is a platform
ceiling on 2 of 6 surfaces. Truth table + MISSING labels are the product. The
one worthwhile follow-on (already implied by 2a): after TikTok Direct Post is
approved, confirm post-publish metrics flow for *published* (not just draft)
videos, and update the truth table row.

## 3. Freeze proposal

The repo is at its healthiest point of the year: main green, zero open PRs,
every surface count machine-checked, every platform claim in docs matched to
live reality. That is an accident of timing, not a steady state — three
consecutive audit waves each surfaced new doc/claim drift created by feature
PRs that outran their verification.

Proposed policy, effective on this memo's merge:

1. **No new feature PRs without an acceptance card.** A feature PR must name a
   kanban task (or issue) that states observable acceptance criteria. "Nice to
   have" gets an issue, not a branch.
2. **CI stays green as a standing obligation.** Any PR that makes main red is
   the author's to fix within one working day, `--admin` merge allowed for
   tiny generated-docs repairs per existing convention.
3. **Exempt from the freeze:** bug fixes with a reproducing test, security
   fixes, docs corrections, CI/release-lane work, and the auth-gap work above
   (it is the point of the freeze — everything else waits so these can land
   cleanly).
4. **Revisit at the TikTok audit verdict** (or +6 weeks, whichever first): the
   freeze exists to converge, not to fossilize.

Rationale: xPST's moat is trustworthiness for humans *and* agents — a green
tree, machine-checked claims, honest labels. Additional features on top of an
unaudited TikTok publish path add surface without adding product. Close the
three auth edges, hold the line on CI, and the differentiated scope in §1 is
defensible in one sentence, which is what a pivot memo should buy.
